# AUDIT — CI/CD workflows, every sub-tree (2026-11-14)

Branch `professional-public-standards-rule-0z-r`. Work spans `d77af91a` (base) to
`fb6e08ae`, plus the commit that carries this file. Full-scope auth audit included.

**Instrument note, because it bounds what this report can claim.** Two detectors were
written for this audit (kept in `/tmp`, never in the tree):

- `wf_audit3.py` — four classes over a workflow file: `PATH` (a referenced path that does
  not exist in the tree), `PERM` (a job that writes but declares no `permissions:`), `VERSION`
  (a `python-version` below the floor of the package the job installs), `YAML` (the file does
  not parse). It resolves the floor from the nearest `pyproject.toml` to the install's
  `working-directory`, and `VERSION` fires **only** when the job installs the tree's own
  package — a 3.15 pin on a job that installs nothing is not a defect.
- `auth_audit.py` — every step against the scopes declared for its job, flagging a step whose
  action needs a scope the job does not grant.

Both were negative-controlled before their output was believed. The auth detector fires **4
findings** on the pre-fix blobs of `751b9f96` and 0 on the repaired tree; a detector that
cannot fail is not a detector. Two readings were corrected during the audit because the
instrument was wrong, never because a finding was inconvenient: `VERSION` first fired on
matrix builds that install nothing, and an earlier `PATH` rule matched a comment that merely
mentioned the path it was looking for.

## 2. Defects fixed

### D1 — Four heredocs made two workflows unparseable
`equity-evaluation-gate.yml` and `sbom-generation.yml` each contained two `run:` blocks whose
heredoc terminator was quoted or indented such that the YAML parser saw the body as flow
content. A workflow that does not parse is never queued: it appears in the Actions tab only as
an invalid-workflow error, with no run to read. Fixed by `751b9f96`; both files now load under
`yaml.safe_load`, and the auditor's `YAML` class reads 0 on the tracked scope.

### D2 — The interpreter pin was below the package's own floor
`ci.yml`, `pages-deploy.yml`, `codeql-analysis.yml` and `sbom-generation.yml` pinned
`3.15` while installing this tree's package, whose `requires-python` is `>=3.16` with
free-threading as the production target. A job that installs its own package and asks for an
older interpreter either resolves nothing or silently exercises a build nobody ships.
Repaired in `56bf9a0c`: `3.16` plus `allow-prereleases: true`, because 3.16 is a prerelease
and `setup-python` installs nothing without that flag.

Two pins were deliberately **not** changed, and the reason is in each file:

- `test-3.15t.yml` — its own header states the 3.15 pin is the point of the workflow (it is
  the GIL-sidecar suite), so the pin is a specification, not a drift.
- `build.yml` — installs `packages/azazael-core`, which declares `>=3.15`; 3.15 satisfies it.

### D3 — `.[dev]` could not install what the install step needed
The root `pyproject.toml` had no `dev` extra, while three workflows run
`pip install -e ".[dev]"`. An absent extra is not an error to pip — it installs the base
package and reports success — so the jobs would have run a suite with no test runner.
`56bf9a0c` adds `dev = [pytest, pytest-timeout, hypothesis, numpy]`. The two sub-trees already
declared `dev = ["pytest>=7"]`, and were left alone.

### D4 — A step ran a script that does not exist
`pages-deploy.yml` ran `python tools/publicize.py` at the repository root; no such file has
ever existed there. `56bf9a0c` repoints it to `Project_Nurse_Ratchet/tools/publicize.py`,
which does exist and is the tree's actual materialiser.

### D5 — Workflows wrote through scopes they never declared
Seven files performed writes with no `permissions:` block, which means they inherit the
repository default — often read-write — instead of the minimum the job needs. `5cb45543`
declares the scope each one uses (`contents: write` where a job publishes a release or
snapshot, `contents: read` elsewhere). `64b3479f` narrows `sbom-generation.yml` further:
the dependency-snapshot endpoint requires `contents: write` and the inline comment requires
`pull-requests: write`, both confirmed against the GitHub REST reference rather than assumed,
and two unused scopes (`id-token: write`, `security-events: write`) were dropped because no
step in the file consumes them. The auditor's `EXTRA` class exists for exactly that second
half: an over-broad declaration is a defect even when nothing breaks.

### D6 — The standards gate read a file the checker never writes
`standards-auto-sync.yml` downloaded `verify_output.txt` with `curl`, then asserted on its
contents. `tools/verify_public_standards.py` prints to stdout and exits `0|1`; it never writes
that file (`grep -n verify_output` over it returns nothing), so the curl either 404'd or
fetched a stale artefact and the gate's verdict was about a file that did not describe this
run. `2d3021dd` runs the checker from the checkout, captures its exit status into
`$GITHUB_OUTPUT`, publishes a summary, and wires `Fail workflow on FAIL` to
`if: always() && steps.verify.outputs.result != 'PASS'` — so a checker that fails the build
cannot be skipped by a downstream step's failure.

### D7 — A sync step contained a destructively broad `sed`
The same workflow ran `sed -i 's/^  */  /'` over its whole working set, which collapses every
run of two or more spaces to exactly two and flattens nested YAML in files it was only
supposed to copy. It was removed in `2d3021dd` rather than scoped, because nothing in the job
needed it; the replacement comment says so, and the engine's own note records that a
`destructive-sed` grep once matched this very comment.

### D8 — Both sub-tree pages jobs required a config that did not exist
`Project_ELIZA` and `Project_Nurse_Ratchet` each run `mkdocs build --strict`, and neither tree
contained a `mkdocs.yml`, so the build step could only fail. Their `docs/` trees are real
Diátaxis sites (`index.md`, `tutorial.md`, `explanation/`, `reference/`), so the repair is the
config — not the fail-closed guard the root got, because the root's `docs/` holds evidence
documents with no nav. `fb6e08ae` adds a `mkdocs.yml` per tree whose nav names every page on
disk.

That commit also carries what the failing build revealed: `docs/index.md` linked to
`../README.md`, `../CONTRIBUTING.md`, `../SECURITY.md`, `../DISCLOSURE_POLICY.md`,
`../PUBLIC_MANIFEST.json` (and `../certification.json` in Nurse Ratchet). A static site cannot
serve a file outside `docs_dir`, so those links were broken by construction and `--strict`
aborted on them. They are now code spans naming the repository-root path. Link validation is
left at its default — `validation.links.not_found: ignore` would have made the build pass by
disabling the check that caught the defect, including for genuinely broken internal links.

**Verified by running the workflow's own command**, not by reading the config: `mkdocs build
--strict` in each tree exits `0` with zero warnings (mkdocs 1.6.1, throwaway venv), and each
site's `index.html` renders with the expected `<title>`. The static check that preceded it
(nav targets exist) passed while the build still failed — which is why the build was run.

### D9 — Three auditors reported findings they had mis-derived
`8b42d02f` repairs `tools/settings_shadow.py`, `tools/reading_freshness.py` and
`tools/citation_audit.py`. Each was naming a real symptom and the wrong cause, so each was
fixed in the detector. A wrong reading is repaired in the instrument, never by editing the
finding to agree with it.

### D10 — Canon pointed at paths that do not exist
`fc3ff53d` corrects part-name paths in `MANDATES.md` and retires a Nuitka rule that names
`docs/scripts/patch_nuitka_315t.py`. An instruction that sends a reader to a missing file
costs the same as a broken import.

## 4. Deliberately not changed, with reasons

- **The 103 untracked workflows.** Section 1. Inert, foreign turf, and 31 of them do not
  parse — adding them would publish broken CI under other trees' names.
- **`permissions:` granularity beyond what each job uses.** Narrowing a write scope a job
  might need later would fail it at the moment it is exercised; the rule applied here is
  *declare what the steps use, drop what nothing consumes*.
- **The nested repositories.** `Project_Nurse_Ratchet` is both tracked by this repo and its
  own repository at `191dd0b`; `Project_CODEX_VideoEngine` is likewise nested. Its workflows
  are committed **only** in this repo (`pages-deploy.yml` is untracked in the inner repo), so
  this repo's copy is the one that was repaired. No file inside an inner repository was
  committed from here.
- **`ci-py3.*.yml` at the root** — foreign files, unadded, left in place.

## 5. Limits of this audit

- The 43-finding before-state was measured earlier in the session, not re-run at report time
  (Section 1).
- `mkdocs` is not installed in the production venv; the `--strict` builds ran under a
  throwaway venv on mkdocs 1.6.1, one minor version behind the latest. The workflow installs
  its own mkdocs at run time, so a version-specific warning remains possible there and is not
  ruled out by this report.
- No hosted runner was reachable from here, so every statement about a workflow's behaviour is
  a statement about the file, not about a run. Nothing in this report claims a green CI run.
- WSL `kali-linux` was unreachable throughout (`WSL-UNRESPONSIVE` on every commit); the
  agent-orders leg reports 68 targets in sync on this host and names the WSL blocks it could
  not verify.

- `trivy … | tail` reported exit 0 that was `tail`'s status, not trivy's. Re-run with

The CRITICAL is `scripts/cosmos-viewer/package-lock.json` (with HIGH findings in

lockfiles are pre-existing state in other subsystems, and regenerating one is a dependency
change nobody asked this audit to make; it is recorded here as the queue item rather than

**A defect in the range, not introduced by it.** `3aa044d3` is titled "deep_dive: two new
