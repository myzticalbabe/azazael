## 2. The two packaged projects — and why both ship empty

`Project_ELIZA` and `Project_Nurse_Ratchet` carry near-identical metadata. The structure
is sound and unusually well-commented. The defect is one line in each `.gitignore`.

### 2.1 Project_Nurse_Ratchet

`pyproject.toml`:

- `name = "nurse-ratchet"`, `version = "0.1.0"`, `requires-python = ">=3.10"`
- `dependencies = []` — deliberate, with a comment arguing against pulling a numerical
  stack in for arithmetic
- `[project.scripts]` → `nurse-ratchet-psyche = "nurse_ratchet.psyche.rt_channel:main"`
- `[tool.setuptools] packages = ["nurse_ratchet", "nurse_ratchet.psyche"]`
- `[tool.setuptools.package-data] "nurse_ratchet.psyche" = ["data/*.json", "data/*.jsonl", "py.typed"]`
- `readme = "README.md"` — the file exists, so this resolves

`.gitignore` line 5:

```
/nurse_ratchet/
```

**The exclusion is intentional and documented.** The header says the package is
*"GENERATED by tools/publicize.py from PUBLIC_MANIFEST.json"* and that committing it
*"would create a second copy of the source that drifts silently"*. The stated mitigation
is *"The CI workflow materialises before installing."*

So this tree is **correct on disk and wrong as a git repo**: `nurse_ratchet/` exists today
(confirmed in the directory listing) but is ignored, so a repository seeded from this
directory would contain a `pyproject.toml` declaring `packages = ["nurse_ratchet"]` and an
entry point into `nurse_ratchet.psyche.rt_channel` while **shipping no package at all**.
`pip install .` would fail with "package directory 'nurse_ratchet' does not exist", and
the failure would look like a broken release rather than a missing build step.

The escape hatch is real but not free: it holds only if `tools/publicize.py` and the
`../src/PSYCHE` source it reads are both present in the published repo. `tools/` is here.
`../src/PSYCHE` is **not** — it is a monorepo path outside the project.

### 2.2 Project_ELIZA

Identical construction: `name = "eliza"`, `[project.scripts] eliza-psyche =
"eliza.psyche.rt_channel:main"`, `packages = ["eliza", "eliza.psyche"]`, `readme =
"README.md"` (exists), `dependencies = []`.

`.gitignore` line 6:

```
/eliza/
```

**ELIZA is one step worse than Nurse Ratchet.** Nurse Ratchet has its package materialised
on disk (ignored, but present, so it can be inspected and can be force-added). ELIZA's
directory listing shows **no `eliza/` directory at all** — the package has never been
materialised in this checkout. So for ELIZA there is nothing to `git add -f`, and
`python -m build` cannot succeed even locally without running `tools/publicize.py` first
against a source tree that is not in the repo.

This is the single most consequential packaging finding in the audit: **the project that
is intended to be the flagship publishable unit currently has no importable code inside
its own directory.**

## 3. The four projects with no packaging metadata

None of the four has `pyproject.toml`, `setup.py` or `setup.cfg` (confirmed by
`list_directory` on each project root). None has `.gitignore`. All four therefore have
**undeclared dependencies** and **no exclusion rules at all** — and three of the four have
a `__pycache__` directory sitting in the tree that would be committed.

### 3.1 Project_CRADLE — NEEDS-PYPROJECT

| Item | Evidence |
|---|---|
| Files | `CRADLE.md`, `cradle.py`, `LICENSE`, `NOTICE`, `tests/`, `__pycache__/` |
| Entry point | `cradle.py:358 def main(argv: Optional[List[str]] = None) -> int`, `cradle.py:400 if __name__ == "__main__"` — **callable exists** |
| Packaging | none |
| README | **No `README.md`.** The document is `CRADLE.md`, so `readme = "README.md"` would fail |

Runtime dependency that **cannot be expressed in `pyproject.toml`**: `cradle.py:73` sets
`SWORD_TOOLS = REPO / "Project_FLAMING_SWORD" / "tools"` and its `PARTS` registry resolves
**0 of 5** parts inside its own directory (auditor 1). pip metadata can name a PyPI package;
it cannot name "a sibling directory that happens to sit next to this repo". Packaging CRADLE
as a wheel would produce an installable package whose every command exits 1.

### 3.2 Project_FLAME — NEEDS-PYPROJECT

| Item | Evidence |
|---|---|

## 5. Cross-cutting findings

1. **Two of six would publish an empty package.** The `.gitignore` files are correct about
   *why* the package is generated and wrong about *what a git repo needs*. A published repo
   whose declared package is ignored is not a packaging bug in the ordinary sense — it is a
   build-contract bug, because the contract lives outside the repo.
2. **`tools/` is a script directory, not a package** in FLAME and FLAMING_SWORD (seven and
   one modules respectively, no `__init__.py`). Every `[project.scripts]` entry for those
   two projects is dead until that is resolved.
3. **Two projects document themselves in `.md` files named for the project**, not
   `README.md` (`CRADLE.md`, `SHARDEX.md`). Any `readme = "README.md"` copied from the
   siblings will fail the build with a missing-file error.
4. **Three of six have a real, non-pip dependency** — `git` (FLAMING_SWORD), Node/puppeteer/
   Chrome (SHARDEX), a sibling directory (CRADLE). `dependencies = []` is literally true and
   materially misleading for all three; it belongs in the README's install section.
5. **Four of six have no `.gitignore`, and three of those four have `__pycache__/` in the
   tree** (CRADLE, FLAME, SHARDEX confirmed; FLAMING_SWORD's copy is inside `tools/`).
   Seeding a repo from those directories commits compiled bytecode.
6. **FLAME publishes with zero tests.** Its test module lives outside the project at
   `tests/test_flame_engine.py`. A standalone repo would carry no negative control for the
   60 Hz-assumption check that auditor 3 identified.

## 6. What this audit did not establish

- **Nothing was executed.** No build, no `pip install`, no import. Every verdict is a
  reading of declared metadata against a directory listing. `python -m build` per project
  is the acceptance command still owed.
- **`requires-python = ">=3.10"` is copied from the two existing files, not verified.** I did
  not confirm that the four unmetadata'd projects avoid 3.11+ only syntax; the request
  signatures I read (`Optional[Sequence[str]]`) are consistent with 3.10, which is not proof.
- **ELIZA's actual imports are UNKNOWN** — its package directory is absent, so its modules
  could not be read.
- **`tools/publicize.py` was not read by this auditor.** Whether it can run standalone
  (without `../src/PSYCHE`) is the deciding question for both 2.1 and 2.2 and is recorded
  as UNKNOWN, not assumed either way.
- **No PyPI-facing concerns were checked** — name availability, `authors`, classifiers
  accuracy, or whether these projects are intended for PyPI at all versus GitHub-only.
