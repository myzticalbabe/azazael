## 2. Blocking defects

### D1 — Three of five workflows request Python 3.15 without `allow-prereleases`

`compliance.yml:29`, `build.yml:23`, `catchall-guard.yml:24` all pin `python-version: '3.15'`
and omit `allow-prereleases: true`. `setup-python` will not resolve a pre-release version
unless that flag is set — the two workflows that do set it (`test-3.15t.yml`,
`graph-semantic.yml:38`) show the authors knew. **These three jobs fail at the second step**,
before any project code runs. This is the single most likely outcome of a first hosted run:
three red X's that say nothing about the code.

*Remediation:* add `allow-prereleases: true` to all three, or pin a version `setup-python`
actually serves. Do not do both-and-hope: pick one and comment which.

### D2 — `compliance.yml` writes stderr into a JSON artifact, then parses it

`compliance.yml:38`:

```
python src/CORE/compliance/scanner.py --report --dir src --format json > compliance_report.json 2>&1
```

`2>&1` merges stderr into `compliance_report.json`. That file is then (a) uploaded as the
`compliance-findings` artifact and (b) `json.load`ed by the Summary step. Any warning, any
deprecation notice, any traceback makes the artifact invalid JSON and turns the Summary step
into a `JSONDecodeError`. The artifact a reviewer downloads is then not the report.

*Remediation:* drop `2>&1`, let stderr go to the log, keep the redirect to stdout only. Better:
have the scanner write the file itself (`--output`), so the shell never assembles a report.

### D3 — `compliance.yml` computes an exit code nothing reads

The scan step publishes `exit_code=$?` into `$GITHUB_OUTPUT` under `id: scan`, and no later
step references `steps.scan.outputs.exit_code`. Combined with the fact that the scanner is
invoked **without** `--ci` (the flag exists — `src/CORE/compliance/scanner.py:953`, and
`STARTUP.md:30` documents it as "Exit non-zero if findings exist"), the scan cannot fail the
job. The file's own comment concedes this ("The scan above only reports"), and the two
separate gate steps are the real gate. Presenting a report-only scan as a gate is the defect;
either wire `--ci` or delete the unused output.

### D4 — `build.yml` swallows a failing test suite and reports green

```
run: python -m pytest tests/ -v || echo "pytest skipped (known segfault on Python 3.13)"
continue-on-error: true
```

`|| echo` converts **any** pytest failure into a success, and `continue-on-error: true` makes
that permanent. A genuinely broken suite is indistinguishable from the historical segfault this
line was written for. It also cites Python **3.13** while the job pins **3.15** (:23) — the
comment has outlived the condition it describes. A gate that cannot fail is not a gate.

*Remediation:* remove `|| echo`, keep `continue-on-error` only if it names the exact known
failure, and fix the version in the comment.

### D5 — `test-3.15t.yml`'s YAML alias defect was real and is now **fixed** (confirming, not complaining)

The historical defect is documented in-file at the `Upload results` step: `path: *.log` is not
a glob to YAML — a leading `*` is an alias — and the document failed `yaml.safe_load`
outright, which was a second independent reason the workflow could never run. It now reads
`path: "*.log"` (quoted). **I checked all five files for siblings of that pattern and found
none**: no other value begins with an unquoted `*`. This one is closed.

### D6 — `build.yml` publishes a committed binary

`packages/azazael-core/azazael-core.exe` is present in the working tree (verified by
`list_directory`). The workflow builds the same file and uploads it. Publishing a repo that
carries a build artifact in source means the "reproducible build" claim cannot be tested — the
checked-in `.exe` may not be the one the workflow produces. `cli.dist/` is present alongside it.

## 5. Cross-cutting hygiene (non-blocking, but all absent)

1. **No `permissions:` block anywhere.** Every job runs with the default `GITHUB_TOKEN`
   scope. `build.yml` creates releases (`softprops/action-gh-release@v2`), which needs
   `contents: write`; granting it implicitly is least-privilege debt.
2. **No `concurrency:` group.** Rapid pushes to `deepseek-engram-813 [renamed to azazael-intel-ultra-9-evo 2026-11-04]` queue duplicate runs.
3. **No `actions/cache`.** Every run reinstalls `basedpyright`, `pytest`, `networkx`,
   `nuitka` from cold.
4. **Actions pinned to major tags, not SHAs** (`@v4`, `@v5`). Tag re-pointing is the
   supply-chain hole SLSA provenance is meant to close; this repo has an SLSA/SBOM thread
   elsewhere, so the mismatch is worth recording.
5. **Four of five jobs run `ubuntu-latest`** for a project whose reference build is a
   Windows 3.15t free-threaded venv. `test-3.15t.yml`'s own header warns that a non-`t`
   interpreter changes results. `compliance`/`catchall-guard`/`graph-semantic` on Linux is an
   untested combination, not a neutral one.
6. **`catchall-guard.yml` throws away its JSON.** The guard is run with `--json` and nothing
   uploads or parses it; findings exist only in the job log, so a reviewer cannot diff them.

## 7. Ordered remediation

1. **D1 first** — otherwise the first hosted run produces three meaningless red builds and
   teaches the wrong lesson. Add `allow-prereleases: true` to `compliance.yml`,
   `build.yml`, `catchall-guard.yml`.
2. **D2** — stop merging stderr into the JSON report before anyone downloads it.
3. **D4** — remove the `|| echo` that makes a failing suite green.
4. **D3** — wire `--ci` or delete `steps.scan.outputs.exit_code`; do not keep a report that
   looks like a gate.
5. **Validate before announcing** — run every workflow via `workflow_dispatch` on a branch
   **before** the repo is made public, and treat the first run as discovery (this repo's own
   handoff notes already say so).
6. Then hygiene: `permissions:`, `concurrency:`, action SHA pinning.
