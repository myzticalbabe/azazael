| probe | functions failing | what it actually measures |

| PF20/PF21 | 1 / 4 | unbounded / non-advancing loop |

Sorted by *severity* rather than count, the shape changes completely. PF04 and
PF02 together are 1799 findings and carry no risk: they are review cost. The
probes that describe functions the system cannot test, cannot reach, or cannot
see failing total **764** — and those are the ones that can hold a live defect
indefinitely.

The single most load-bearing number is **PF17 = 532**: 38% of the mesh is
unreachable by any test. PF16 = 114 of those are reachable by *nothing at all*.
A function nothing calls cannot regress visibly, so it cannot be trusted and
cannot be fixed by observation — only by reading. That is the actual debt, and
it is an order of magnitude older than anything the monitors were showing.

### The probes were the first thing that had to be debugged

Four of the twenty-one probes were false-positive generators on first run, and
each failure taught the same lesson at a different grain:

1. **PF13** flagged 13 "constant-true `while` with no break" — all 13 were
   `while flag:` / `while True` bodies bounded by a `return`. The probe matched
   on the *literal* rather than the body. Fix: constant-`True` only, plus a new
   **PF21** for the genuinely risky shape (a loop whose body may not advance its
   own condition).
2. **PF20** flagged every `for` loop. A `for` over a collection is bounded by
   construction; only recursion needs a depth guard. Fix: recursion only.
3. **PF15** as originally written would have flagged `except ...: pass` that
   sets a flag first. Fix: require the `pass` to be the *entire* handler body.
4. **PF21** then found 4 real candidates and cleared all 4 on reading — but
   surfacing them is the point. A probe that has never produced a false
   positive has not been calibrated, it has been avoided.

**Inference:** an auditor is a measuring instrument, and this session's first
two hours went to calibrating the instrument rather than acting on its output.
That is not overhead. Acting on the uncalibrated census would have produced 13
fabricated "unbounded loop" fixes and destroyed the signal for the 4 real ones.

## 2. What the audit actually found (fixed)

All three bugs came out of the P0 triage, and all three share a family
resemblance: **the code reports success without having established the
precondition for it.**

### 2.1 `EvolutionEngine.evolve` — lost-update race (P0, PF18/PF21 path)

Snapshot `self._population` under `self._lock`, spend a whole generation on
crossover and mutation *outside* it, then write back under the lock without
checking whether another caller had already finished. Two concurrent callers
both snapshot the same parents, both write, and one **entire generation of
offspring is silently discarded** while `self._generation` advances twice. The
monitors would show a healthy fabric running twice as fast as it was.

Fixed with a fencing token (`fencing.py`, §3.1). The re-check is part of the
commit, so it cannot be forgotten by the next author.

### 2.2 `optimize_multi_objective` — `IndexError` on objective/survivor overflow

Elite slots are allocated backwards from the end (`slot = -(obj_idx + 1)`). With
more objectives than survivors the negative index walks off the front of
`new_population` and the exception escapes the whole optimization. Guarded by
`len(new_population) > obj_idx`. This is the class of bug that only appears when
someone adds a fourth objective years later.

### 2.3 `moead_weights` — weights that do not sum to 1

The Das–Dennis fallback drew **twice** for `n_obj == 2`:

```python
(random.random(), 1.0 - random.random())[:n_obj]
```

Tchebycheff scalarisation assumes `a` and `1 - a`. Two independent draws give an
arbitrary sum, so every comparison performed with those weights is mis-scaled
by a random factor — a silent quality regression in exactly the branch that only
runs when the lattice under- or overshoots. Now one draw per pair. The old
`[:n_obj]` also sliced a 2-tuple on a path only reachable for `n_obj == 2`,
which is what hid the mismatch from review.

**Inference across all three:** none of these would have produced a traceback,
a log line, or a red monitor. Each produced *plausible output*. That is the
signature of the defect class this audit was worth running for, and it is
invisible to monitoring that only watches for failure — see §4.2.

## 3. Applied primitives (new code)

Both of the first two insights were applied as primitives rather than as
call-site fixes, because the audit showed the *shape* recurring (PF18 = 15
functions write module-level state; PF15 = 118 handlers swallow evidence).

### 3.1 `CORE/WORMS/expansion/fencing.py` — fencing tokens for in-process state

Kleppmann's fencing tokens, reapplied from distributed locks to in-process
shared state. A writer mints a monotonic token *before* it starts, does its
expensive work unlocked, and the commit path — the only path that writes —
verifies the token is still the newest. A stale write becomes unrepresentable
rather than merely discouraged.

Three properties make it more than a remembered check:

- **Process-wide, not per-instance.** The bug it targets is two *instances* (or
  two threads) racing one resource. An instance lock cannot see the other
  instance; the fence can.
- **Never blocks, never raises.** A fence is a rejection mechanism, not a mutex.
  Contention resolves to one winner and a report, which is what free-threaded
  3.14t wants.
- **Counters are trendable.** `fence_report()` exposes claims/commits/rejections,
  so contention becomes a measurement instead of a mystery.

Wired into `evolve()`; `tests/test_mesh_audit_insights.py` covers stale-token
rejection, two-instance racing, and the failed-apply-does-not-burn-the-token
case.

### 3.2 `CORE/WORMS/expansion/silence.py` — the silent-failure ledger

118 handlers absorb a failure and say nothing. Individually defensible;
collectively they destroy the *distinction* between

- the fabric degraded gracefully and healed on the next cycle, and
- the fabric has been failing to load its own learning on every start for a week.

Both produce byte-identical behaviour. This is not hypothetical — earlier in
this same session, a stale spine store silently served synthetic fixtures, and
it was found by a human reading a file, not by the system noticing.

The insight is that a swallowed exception is **not a control-flow decision, it
is a measurement**, and `pass` throws the measurement away. So:

- **Signature clustering is the alarm, not the total.** A tag whose count rises
  is usually fine (a flaky peer). A tag that grows a *new* exception type is a
  failure mode nobody predicted, wearing the costume of the one they did. The
  ledger therefore tracks distinct `type(msg)` signatures per tag, bounded at 24.
- **Budgets make "graceful" checkable.** A tag declares how many failures it may
  absorb. Past budget, the swallow is no longer degradation, it is a hidden
  fault, and `tripped()` says so. `budget=0` means "this failure is a fault".
- **It cannot fail.** Every entry point is wrapped; a ledger that can itself
  raise is worse than no ledger.

## 4. Inferred insights (not yet applied)

### 4.1 The mesh needs a **non-occurrence** signal, not more occurrence monitoring

Every existing monitor is occurrence-driven: it renders what *happened*. Three
of the three bugs found here are, by construction, things that did **not**
happen — a generation that never committed, an objective that was never
evaluated, a weight vector that was never valid. Nothing in the architecture
records an expected event that failed to appear.

The primitive would be a **liveness obligation**: a named expectation with a
deadline, minted by the code that should cause it and discharged when it fires.
"Generation N+1 must commit within T" is then a first-class fact the monitors
can go *red* on, and its absence is the signal — which is precisely the class of
failure this audit keeps finding. Fencing's `rejections` counter and the
silence ledger's `tripped()` are both already half of this: they are the only
two places in the mesh today that record a negative.

### 4.2 PF17 = 532 says the mesh is **wider than it is deep**

38% of functions are reached by no test. The architectural reading is that the
fabric grew by accretion — each session added capability (226 worms, 35
categories, 70 routes) and verified the new path only. The correct response is
not to write 532 tests. It is to **derive the coverage obligation from the
reachability graph**: a function that nothing references (PF16 = 114) should be
either wired or explicitly retired, and that decision should be *data*, the way
`SERVED_ENGINES` / `UNSERVED_ENGINES` in `evolution.py` already encodes the
wire-or-cut verdict for the v2 engines. That pattern worked; it should be the
general answer to PF16, not a one-off.

### 4.3 The probe census should be persisted and trended

`tools/mesh_function_preflight.py` is deterministic and cheap. Running it each
session and diffing the census would turn annotation and coverage debt into a
time series — the same move that made the silence ledger valuable. Currently the
census is a snapshot that dies with the session.

**Bleeding edge worth evaluating:** the probe battery is a static analyser
whose *false-positive rate is itself measurable* (this session measured it:
4 of 21 probes miscalibrated, all cleared by reading). A mesh that runs its
auditor and counts how many findings a human rejected has a supervision signal
for refining the auditor — and, more interestingly, a way to detect when the
**auditor's precision** is drifting as the codebase changes. Aligning audit
precision over time is a small, well-posed optimisation problem the architecture
already has all the data for.

## 5. Reflection — what this session changed about the method

1. **Calibrate the instrument before acting on the reading.** 4 of 21 probes
   were wrong on first run. Acting first would have manufactured 13 fake fixes.
2. **Severity, not count, orders the work.** PF02+PF04 outnumber the risky
   findings 2:1 and carry none of the risk.
3. **Prefer a primitive to a call-site fix when the shape recurs.** Both new
   modules exist because the audit showed the same pattern at 15 and 118 sites.
   A fix applied 118 times is a fix that will be forgotten 118 times.
4. **Falsifiable reporting beats success-shaped reporting.** `save_checkpoint`
   used to return a success dict while persisting nothing. It now reports
   `persisted` and `persist_error`, and `_get_store` retries a transient lock
   instead of converting one lock into a permanently missing checkpoint. The
   general rule: **if a function cannot fail, its caller cannot know.**
5. **Verify the verifier.** Two of the new helpers had a bug that only the
   verification step caught (the scanner's same-line span check returning on the
   first span instead of checking the rest). Tests written *for* a fix are not
   independent confirmation of it.
