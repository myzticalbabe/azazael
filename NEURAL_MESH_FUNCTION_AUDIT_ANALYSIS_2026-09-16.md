Sorted by *severity* rather than count, the shape changes completely. PF04 and
PF02 together are 1799 findings and carry no risk: they are review cost. The
probes that describe functions the system cannot test, cannot reach, or cannot
see failing total **764** — and those are the ones that can hold a live defect
indefinitely.

The single most load-bearing number is **PF17 = 532**: 38% of the mesh is
unreachable by any test. PF16 = 114 of those are reachable by *nothing at all*.
A function nothing calls cannot regress visibly, so it cannot be trusted and
cannot be fixed by observation — only by reading. That is the actual debt, and
it is an order of magnitude older than anything the monitors were showing.

### The probes were the first thing that had to be debugged

Four of the twenty-one probes were false-positive generators on first run, and
each failure taught the same lesson at a different grain:

1. **PF13** flagged 13 "constant-true `while` with no break" — all 13 were
   `while flag:` / `while True` bodies bounded by a `return`. The probe matched
   on the *literal* rather than the body. Fix: constant-`True` only, plus a new
   **PF21** for the genuinely risky shape (a loop whose body may not advance its
   own condition).
2. **PF20** flagged every `for` loop. A `for` over a collection is bounded by
   construction; only recursion needs a depth guard. Fix: recursion only.
3. **PF15** as originally written would have flagged `except ...: pass` that
   sets a flag first. Fix: require the `pass` to be the *entire* handler body.
4. **PF21** then found 4 real candidates and cleared all 4 on reading — but
   surfacing them is the point. A probe that has never produced a false
   positive has not been calibrated, it has been avoided.

**Inference:** an auditor is a measuring instrument, and this session's first
two hours went to calibrating the instrument rather than acting on its output.
That is not overhead. Acting on the uncalibrated census would have produced 13
fabricated "unbounded loop" fixes and destroyed the signal for the 4 real ones.

## 2. What the audit actually found (fixed)

All three bugs came out of the P0 triage, and all three share a family
resemblance: **the code reports success without having established the
precondition for it.**

### 2.1 `EvolutionEngine.evolve` — lost-update race (P0, PF18/PF21 path)

Snapshot `self._population` under `self._lock`, spend a whole generation on
crossover and mutation *outside* it, then write back under the lock without
checking whether another caller had already finished. Two concurrent callers
both snapshot the same parents, both write, and one **entire generation of
offspring is silently discarded** while `self._generation` advances twice. The
monitors would show a healthy fabric running twice as fast as it was.

Fixed with a fencing token (`fencing.py`, §3.1). The re-check is part of the
commit, so it cannot be forgotten by the next author.

### 2.2 `optimize_multi_objective` — `IndexError` on objective/survivor overflow

Elite slots are allocated backwards from the end (`slot = -(obj_idx + 1)`). With
more objectives than survivors the negative index walks off the front of
`new_population` and the exception escapes the whole optimization. Guarded by
`len(new_population) > obj_idx`. This is the class of bug that only appears when
someone adds a fourth objective years later.

### 2.3 `moead_weights` — weights that do not sum to 1

The Das–Dennis fallback drew **twice** for `n_obj == 2`:

```python
(random.random(), 1.0 - random.random())[:n_obj]
```

Tchebycheff scalarisation assumes `a` and `1 - a`. Two independent draws give an
arbitrary sum, so every comparison performed with those weights is mis-scaled
by a random factor — a silent quality regression in exactly the branch that only
runs when the lattice under- or overshoots. Now one draw per pair. The old
`[:n_obj]` also sliced a 2-tuple on a path only reachable for `n_obj == 2`,
which is what hid the mismatch from review.

**Inference across all three:** none of these would have produced a traceback,
a log line, or a red monitor. Each produced *plausible output*. That is the
signature of the defect class this audit was worth running for, and it is
invisible to monitoring that only watches for failure — see §4.2.

## 3. Applied primitives (new code)

Both of the first two insights were applied as primitives rather than as
call-site fixes, because the audit showed the *shape* recurring (PF18 = 15
functions write module-level state; PF15 = 118 handlers swallow evidence).

### 3.1 `CORE/WORMS/expansion/fencing.py` — fencing tokens for in-process state

Kleppmann's fencing tokens, reapplied from distributed locks to in-process
shared state. A writer mints a monotonic token *before* it starts, does its
expensive work unlocked, and the commit path — the only path that writes —
verifies the token is still the newest. A stale write becomes unrepresentable
rather than merely discouraged.

Three properties make it more than a remembered check:

- **Process-wide, not per-instance.** The bug it targets is two *instances* (or
  two threads) racing one resource. An instance lock cannot see the other
  instance; the fence can.
- **Never blocks, never raises.** A fence is a rejection mechanism, not a mutex.
  Contention resolves to one winner and a report, which is what free-threaded
  3.14t wants.
- **Counters are trendable.** `fence_report()` exposes claims/commits/rejections,
  so contention becomes a measurement instead of a mystery.

Wired into `evolve()`; `tests/test_mesh_audit_insights.py` covers stale-token
rejection, two-instance racing, and the failed-apply-does-not-burn-the-token
case.

### 3.2 `CORE/WORMS/expansion/silence.py` — the silent-failure ledger

118 handlers absorb a failure and say nothing. Individually defensible;
collectively they destroy the *distinction* between

- the fabric degraded gracefully and healed on the next cycle, and
- the fabric has been failing to load its own learning on every start for a week.

Both produce byte-identical behaviour. This is not hypothetical — earlier in
this same session, a stale spine store silently served synthetic fixtures, and
it was found by a human reading a file, not by the system noticing.

The insight is that a swallowed exception is **not a control-flow decision, it
is a measurement**, and `pass` throws the measurement away. So:

- **Signature clustering is the alarm, not the total.** A tag whose count rises
  is usually fine (a flaky peer). A tag that grows a *new* exception type is a
  failure mode nobody predicted, wearing the costume of the one they did. The
  ledger therefore tracks distinct `type(msg)` signatures per tag, bounded at 24.
- **Budgets make "graceful" checkable.** A tag declares how many failures it may
  absorb. Past budget, the swallow is no longer degradation, it is a hidden
  fault, and `tripped()` says so. `budget=0` means "this failure is a fault".
- **It cannot fail.** Every entry point is wrapped; a ledger that can itself
  raise is worse than no ledger.

## 4. Inferred insights (not yet applied)

### 4.1 The mesh needs a **non-occurrence** signal, not more occurrence monitoring

Every existing monitor is occurrence-driven: it renders what *happened*. Three
of the three bugs found here are, by construction, things that did **not**
happen — a generation that never committed, an objective that was never
evaluated, a weight vector that was never valid. Nothing in the architecture
records an expected event that failed to appear.

The primitive would be a **liveness obligation**: a named expectation with a
deadline, minted by the code that should cause it and discharged when it fires.
"Generation N+1 must commit within T" is then a first-class fact the monitors
can go *red* on, and its absence is the signal — which is precisely the class of
failure this audit keeps finding. Fencing's `rejections` counter and the
silence ledger's `tripped()` are both already half of this: they are the only
two places in the mesh today that record a negative.

### 4.2 PF17 = 532 says the mesh is **wider than it is deep**

38% of functions are reached by no test. The architectural reading is that the
fabric grew by accretion — each session added capability (226 worms, 35
categories, 70 routes) and verified the new path only. The correct response is
not to write 532 tests. It is to **derive the coverage obligation from the
reachability graph**: a function that nothing references (PF16 = 114) should be
either wired or explicitly retired, and that decision should be *data*, the way
`SERVED_ENGINES` / `UNSERVED_ENGINES` in `evolution.py` already encodes the
wire-or-cut verdict for the v2 engines. That pattern worked; it should be the
general answer to PF16, not a one-off.

### 4.3 The probe census should be persisted and trended

`tools/mesh_function_preflight.py` is deterministic and cheap. Running it each
session and diffing the census would turn annotation and coverage debt into a
time series — the same move that made the silence ledger valuable. Currently the
census is a snapshot that dies with the session.

**Bleeding edge worth evaluating:** the probe battery is a static analyser
whose *false-positive rate is itself measurable* (this session measured it:
4 of 21 probes miscalibrated, all cleared by reading). A mesh that runs its
auditor and counts how many findings a human rejected has a supervision signal
for refining the auditor — and, more interestingly, a way to detect when the
**auditor's precision** is drifting as the codebase changes. Aligning audit
precision over time is a small, well-posed optimisation problem the architecture
already has all the data for.

## 5. Reflection — what this session changed about the method

1. **Calibrate the instrument before acting on the reading.** 4 of 21 probes
   were wrong on first run. Acting first would have manufactured 13 fake fixes.
2. **Severity, not count, orders the work.** PF02+PF04 outnumber the risky
   findings 2:1 and carry none of the risk.
3. **Prefer a primitive to a call-site fix when the shape recurs.** Both new
   modules exist because the audit showed the same pattern at 15 and 118 sites.
   A fix applied 118 times is a fix that will be forgotten 118 times.
4. **Falsifiable reporting beats success-shaped reporting.** `save_checkpoint`
   used to return a success dict while persisting nothing. It now reports
   `persisted` and `persist_error`, and `_get_store` retries a transient lock
   instead of converting one lock into a permanently missing checkpoint. The
   general rule: **if a function cannot fail, its caller cannot know.**
5. **Verify the verifier.** Two of the new helpers had a bug that only the
   verification step caught (the scanner's same-line span check returning on the
   first span instead of checking the rest). Tests written *for* a fix are not
   independent confirmation of it.

## 6. Second pass — the `spine_registry` P0 block

The first pass left the highest-complexity functions untouched:
`load_spine_state` (c=61), `merge_spine_gossip` (c=55), `_merge_disk_state`
(c=36), `record_outcome` (c=29). Working them found four defects, and the
strongest finding of the session is not any one of them — it is that **two of
them are a matched pair, and the code was consistent only by accident.**

### 6.1 `load_spine_state` blind-assigns the Q-table (silent reversion)

The restore path did `_Q_WEIGHTS[k] = clamp(w)` for every restored weight, while
its sibling `_merge_disk_state` — the merge-on-save path — adopted them only
when absent. `load_spine_state()` is public and reachable mid-process, so a live
adaptation was overwritten by the disk copy:

```
saved weight -0.3312  ->  learned to 0.6672  ->  load_spine_state()  ->  -0.3312
```

Both calls report success. The module's own comment above `policy_latest`
states the rule — *"an in-memory adaptation is always newer than the disk one.
Blind assignment would roll a live adaptation back"* — and the weights were the
one table that ignored it. Fixed with `setdefault`.

### 6.2 `_ensure_loaded` latches a skip when memory is non-empty — the pair

Its guard was the emptiness heuristic `not _HOMEOSTAT and not _Q_WEIGHTS`. Any
process that recorded one outcome, or dreamed once, before its first getter set
`_LOADED_ONCE` **without restoring anything**, then ran its whole life on an
empty brainstem. The file existed, `load_spine_state()` was never called, and
nothing anywhere said so.

This is the pair. The emptiness heuristic was safe **only because of 6.1**:
blind assignment plus "load only when empty" is self-consistent. Changing
either alone makes it strictly worse — fix 6.1 alone and the heuristic starts
clobbering live state on every call; fix 6.2 alone and 6.1 fires constantly.
The correct move is both at once, because loading *merges* (setdefault / MAX)
rather than clobbers. A defect that is only a defect in company is invisible to
any per-function review that treats functions as independent — which is exactly
what the TODO's structure encourages.

### 6.3 `dream_reinforce` has no docstring

`_ensure_loaded()` sat **above** the docstring, making it a dead expression
statement and leaving `__doc__` as `None`. The function's entire contract was
unreachable from `help()`, the audit probes and any doc-driven tooling.

### 6.4 `merge_spine_gossip` promises a recency rule it does not implement

Docstring: *"q_weights: the value whose homeostat record is newer wins"*.
Code: `if k not in _Q_WEIGHTS: adopt` — never compares records at all, so once
an env knows a key it refuses a better-informed peer's value forever, and two
envs diverge permanently on that key. The inline comment claimed to check
"newer evidence" too; neither did.

Implemented rather than reworded, because the module's whole design is
convergence (HLC ordering, trust gate, anomaly model adopted only when
better-trained). One subtlety: the comparison must use the *pre-merge* ledger
stamps, since the homeostat loop above replaces those records wholesale and
makes the comparison vacuous — which is likely how the shortcut survived.
Strictly-newer plus counting only real changes keeps the documented idempotency
(idempotency matters here: a re-merge adopting a weight with no ledger record on
either side would otherwise fire forever).

### 6.5 Verified, and verified to fail

Eight regression tests in `tests/test_spine_brainstem_persistence.py`. Run
against the **pre-fix** source, exactly the four tests corresponding to the four
defects fail and the four "must still work" guards pass — restoring absent keys,
peer-newer adoption, one-time adoption, and an unstamped peer that cannot
displace local evidence. A guard that passes before and after is doing its job;
a regression test that passes on the broken code is not.

## 7. The liveness primitive, built

§4.1 proposed it; this pass built it: `CORE/WORMS/expansion/liveness.py`.

Three sorts of miss, because they mean different things: `unfulfilled` (a
one-shot's deadline passed — something specific did not complete), `silent` (a
heartbeat beat at least once and then stopped — something that was working
died), and `never_beaten` (a requirement never beat within its own period — the
producer never started, which is the most common real cause and the one an
occurrence monitor structurally cannot see).

Two design decisions carry the module:

- **`observable` is reported beside `healthy`.** Green with nothing declared is
  *unknown*, not all-clear — the same ambiguity as the 118 silent swallows in
  `silence.py`, one level up. `unmonitored()` names obligations that were
  declared and have since stopped being armed at all, which is invisible to both
  an occurrence monitor and a heartbeat.
- **A miss is reported on every poll while it is unmet.**

That second point is a bug I introduced and then found: the first version
consumed each miss (reported once, then returned a clean board). A monitor
polling every 60s would have seen a fault on one poll and health on the next —
output that decays is indistinguishable from a system that repaired itself,
which is the exact failure class this audit exists to remove. The latch is now
history only (`misses_total` counts distinct misses, not polls).

Wired into the one scheduled entry point (`scripts/run_azazael_chain.py`): a due
job that never starts is the canonical non-occurrence, so arming an obligation
before `_start_slow` and discharging it only on success turns `START-FAIL` from
a log line into machine-readable state.

## 8. Wiring the negatives into the monitors

All three ledgers are **in-process by design**, which is a trap for a monitor:
the renderer is a different process, so importing them there would read empty
dicts and draw a green panel. That is "success-shaped reporting" one level up,
so the contract is explicit instead:

- `publish_failure_visibility()` writes an atomic snapshot; latched misses are
  carried forward so a short-lived publisher's clean run cannot erase another
  process's evidence, bounded by `CARRY_FORWARD_SECONDS` so a fixed fault does
  not linger forever.
- `collect_failure_data()` reports `observed: False` when nothing has published.
- The card renders four states, not two: **faults** (red), **stale publisher**
  (amber — a publisher that stopped *is* the non-occurrence the card exists
  for), **clear** (green), and **unobserved** (grey, explicitly not green).

Two bugs in my own wiring, both caught by reading the rendered panel rather
than trusting the code:

1. `state_age()`'s second value is `is_stale`, not `is-fresh`. I named it
   `fresh` and then tested `not fresh`, so a snapshot published one second ago
   was labelled "publisher stopped". The variable is now `stale`.
2. The consumption bug in §7 only surfaced through the publish path, because
   the producer's own `snapshot()` call consumed the miss before writing it.

## 9. Wire-or-cut, generalised to every unreferenced function

§4.2 proposed generalising the `evolution.py` pattern; this pass did it.
`tools/mesh_function_preflight.py --verdict` regenerates
`NEURAL_MESH_WIRE_OR_CUT.json`: all **114** PF16 findings, each with a declared
disposition — `wired`, `retired` or `pending` — and re-running preserves
decisions already made.

`pending` is a first-class status on purpose. An unreviewed function is not the
same as a decided one, and collapsing the two is how a backlog becomes a lie;
the count is published so it can be trended rather than assumed zero.

`tests/test_mesh_wire_or_cut.py` asserts the table agrees with reality: no PF16
finding undeclared, no declaration for a function that no longer exists, no
`wired` declaration that nothing actually reaches, no `retired` declaration that
something now depends on (and a retirement must state its reason), and no
unknown statuses. Verified to fail: deleting one declaration fails three of the
eight checks.

This is the general answer to PF16 — the decision is data, and a test holds the
data against the code.

## 11. Pass of 2026-09-18 — PF16 calibration, and what the backlog is made of

### 11.1 PF16 was miscalibrated for protocol methods (instrument fault, not dead code)

**PF16 = 119 live** on this pass, against 117 declared in a table generated
2026-09-16, and `tests/test_mesh_wire_or_cut.py` was **red**: four findings

failure mode a generated table is supposed to make impossible.

Six of the findings were protocol methods the interpreter invokes itself, and
PF16's model — *does the bare name appear as a `Name` or `Attribute`?* — cannot
see such a call **in principle**, because no correct program writes
`obj.__repr__()`. The decisive evidence:

| finding | why the flag is wrong |
|---|---|
| `nerve:_LazyTorch.__bool__` | `bool(_torch)` is called at **four** sites in the same file (L162, 206, 220, 239) |
| `nerve:_LazyTorch.__getattr__` | `_torch.xpu`, `_torch.Generator`, `_torch.nn` all dispatch through it |
| `race_detector:_TracedLock.__getattr__` | delegation proxy; every undecorated attribute access routes through it |
| `NeuralPipeline.__repr__`, `arena:Environment.__repr__`, `morph:Genome.__repr__` | reached by `repr()` and by every debugger/log renderer |

Calibrated with an explicit `PROTOCOL_METHODS` name-set rather than silenced by
inventing callers, because adding a call site to satisfy a probe is exactly the
anti-pattern this table exists to prevent. PF16 fell **119 → 113**; no
non-protocol finding changed. Three tests hold it, including one that reads
`nerve.py` and fails if `bool(_torch)` ever disappears — because the exemption
is only honest while the method is genuinely invoked.

`PF17` has the same blind spot and was **deliberately left alone**: it is a
coverage *signal*, not a disposition, and moving two probes in one pass would
make the census diff unattributable.

### 11.2 B6 fixed — and it was two defects, not one

`synapse:MoEDispatcherWorm.dispatch_cascade` had no caller, so neither half of
B6 had ever executed:

1. **Crash.** `answer` is bound only on a *successful* attempt, but the
   below-threshold fall-through read it unconditionally. Every resolvable expert
   raising therefore produced `UnboundLocalError` — on the one path the

2. **False claim.** The `best_effort_last_expert` note asserted the last expert
   *tried*. After the loop `name` is merely whatever was ranked last, which is

Fixed to return `{"success": False, "error": "all_experts_failed"}` when no
attempt produced an answer, and otherwise to report the **highest-confidence**
attempt as `best_effort_best_expert`. Both halves are pinned by regression tests

## §12. Instrument validation and the stale-artifact audit (2026-09-18)

Applying "this should be able to fix all of this" to the machinery itself found
that four of the numbers the machinery acts on were wrong, and that the two
consumers of the census had never been pointed at it.

### 12.1 The comparator could not tell a duplicate from a coincidence

`DedupAnalyzer` scored worm pairs by Jaccard over method-name sets.
`Jaccard({x}, {x})` is **1.0**, so any two worms sharing a single generic verb
scored `exact_signature` at 1.0 -- and `execute` alone is the whole compared
method set for **86 of 202** worms (`get_summary` 36 more, `scan` 35,
`get_status` 7). Measured on the live fleet: of 6105 pairs, **1529 reached the
threshold and 1529 were rejected by the calibration -- every one a false
positive.** The consumer is the retirement decision, and it proposed retiring
**35 worms including `EvolutionEngine`, `DreamingModule`, `GeneticOptimizer`
and `HypnagogicSynthesizer`**.

Fixed by making a name-level match necessary but not sufficient:
`UNIVERSAL_METHODS` (interface, not capability), `MIN_DISTINCTIVE_SHARED`
(distinctive support), and `MIN_IMPLEMENTATION_SIMILARITY` (the bodies' own

`DedupAnalyzer.self_check()` now validates the comparator on control pairs whose

### 12.2 The registry cache was serving half a fleet

`~/.azazael/worm_registry_cache.pkl` held **111 worms across 24 categories**
while a real scan registers **229 across 35**. It loaded as fresh, so the fleet
came up missing `axon`, `dendrite`, `glia`, `envmesh`, `ml` and `network` with
nothing reporting a problem -- and every consumer inherited it, the queens and
this census included.

Three separate holes:

1. **Freshness was mtime-only.** A registry built from unchanged sources is
   self-consistently "fresh". `_registry_fingerprint()` (content md5 over
   `_REGISTRY_SOURCE_FILES`) now closes it -- the contract
   `test_worm_registry_cache_freshness.py` specified on 09-14 and which had
   **never been implemented** (6 tests red, `_registry_fingerprint` absent).
2. **Currency was mistaken for safety.** `save_cache` now records
   `_coverage = {declared_on_disk, registered, excluded_unpicklable, complete}`
   and `_load_cache_readonly` refuses a cache that cannot represent the
   registry, however current it is.
3. **A swallowed exception produced the staleness.** `save_cache` did a bare
   `pickle.dump`, so one unpicklable entry raised `PicklingError`; the caller
   treated that as non-fatal (`except Exception: pass`) and the cache silently
   kept the registry it held BEFORE. Unpicklable entries are now excluded
   per-entry and reported, and a failed save is logged.

### 12.5 Correction to §11, and one wiring that closed a real defect

§11 says "twenty of the 21 have a production referrer today (`spine.py` for
`SplitBrainResolverWorm.report_fork`, `FederatedAggregatorWorm.run_round`,
`RewardShaperMeshWorm.local_score` and `MeshRouterWorm.invalidate_route` ...)".
**That was wrong, and the error was the same one PF16 had.** Re-measured with
`src/tests/` excluded (a test reference is not a production consumer):

| | count |
|---|---|
| findings on a class WITH a production referrer | 39, across 25 classes |
| findings on a class with NO production referrer | 100, across 61 classes |
| findings with no class in the qualname (module-level) | 35 |

Those "referrers" are references to the **class** -- an import, an
instantiation -- not to the method. `spine.py` imports and constructs
`SplitBrainResolverWorm` and then calls `resolve()`; it never called
`report_fork`, which is exactly why `report_fork` was `pending`.

**And that made the stage structurally incapable of working.** `resolve()` reads
`self._forks[model]` and answers `{"resolved": False, "reason": "no_forks"}`
when the box is empty. `report_fork()` is the only writer, and it had no caller
in the tree -- and `spine.py` built a fresh resolver each cycle, so `_forks` was
empty every time. The model-fork stage therefore reported `no_forks` for every
fork, every cycle, which reads as "there was nothing to resolve" rather than
"the input was never fed in". That is defect B8's shape again: a claimed control
that is not in the control path.

Fixed by reporting each fork before resolving it -- the tuple the stage already
unpacks is exactly `report_fork`'s signature -- and by publishing
`forks_resolved` so a stage that resolves zero is visible instead of looking
like a clean cycle. Verified:

```
before: {'success': True, 'model': 'm1', 'resolved': False, 'reason': 'no_forks'}
after : {'success': True, 'model': 'm1', 'resolved': True,
         'winner': {'env': 'wsl2-ubuntu', 'reward': 0.9, 'hash': 'h1'}, 'dropped': 1}
```

130 passed across the four fabric test files afterwards.

The remaining 38 findings on reachable classes are NOT a mechanical wiring job:
each needs a per-site decision about which stage genuinely consumes the value,
and adding a caller that nothing reads is decoration, which is the anti-pattern
the provider review named. They stay `pending` until that decision is made per
method.
