# PROJECT SHARDEX

Mirror a game's entire codebase, shatter it into shards, and transubstantiate a shard
into **FLAME** — a playable 3D arena whose parameters are generated from that shard, with
a golden state hash that the browser and the tool both agree on.

```bash
python Project_SHARDEX/shardex.py --mirror /path/to/game            # L0
python Project_SHARDEX/shardex.py --shatter --out /path/to/game     # L1
python Project_SHARDEX/shardex.py --forge .shardex/shards/<name> --out flame   # L2
python Project_SHARDEX/shardex.py --golden .shardex/shards/<name>  # the expected hash
python Project_SHARDEX/shardex.py --verify flame                   # does the bundle agree
python Project_SHARDEX/shardex.py --doctor
python Project_SHARDEX/shardex.py --selftest                       # 13 checks
```

Stdlib only. No key, no build, no network.

## The ladder, and where it actually stands

| rung | what it does | state |
| --- | --- | --- |
| **L0 MIRROR** | walks the game's tree once, sha256 per file, role per extension, provenance per file, refuses a source that is not there or holds nothing | **BUILT** |
| **L1 SHATTER** | cuts the mirror into self-contained, content-addressed shards (`name@sha256:<64>`), one per top-level group, bounded by the 24-file / 2 MiB low-end ceilings | **BUILT** |
| **L2 FORGE** | transubstantiates one shard into `flame.json` + `flame.html`: a 3D arena whose size, orb count and seed come from that shard's own content hash, with a golden run computed in Python and in the browser | **BUILT** |
| **L3 TUNE** | a champion edits `flame.json` (or forges with `--tune k=v`); the golden hash moves with the config, so every bracket has a hash it must agree on | **BUILT** |
| **L4 LAUNCH** | brackets, signed result files, replay verification, entry fees, a spectator view | **BUILT** |

## The honest boundary — read this before the marketing writes itself

**FLAME is a playable 3D arena whose parameters are generated from a shard. It is not the
original game's mechanics.**

Extracting a ruleset from arbitrary source code is a research problem. A tool that printed
"your game, resurrected" over a generic arena would be exactly the defect this estate
keeps paying for: a true-looking claim with nothing behind it. What *is* real:

- the arena is **derived** from the shard — `arena` from payload bytes, `orbs` from file
  count, `seed` from the content hash — so two shards forge two different arenas;
- `flame.json` names the shard it came from, and the shell prints that id on screen;
- the golden run is a number, `1c045e596f950543` for the METTHEW `highend_duel` shard,
  that Python and Chrome both compute from the same scripted input.

So the claim SHARDEX makes is: *this shard, at this config, produces this deterministic
arena, and the artifact you are holding is provably that arena.* It does not claim to be
the game the code came from.

## Why a golden hash and not a screenshot

"Playable" is not a test. A state hash is:

- fixed-step sim at `sim_hz`, floats in doubles, the same expression order in both
  languages;
- a **scripted** input (right for 60 ticks, left for 60, jumps at 10 and 70) — an input
  generated by the thing under test would prove only that the generator is consistent
  with itself;
- the state serialised to 4 decimals and hashed with two FNV-1a 32-bit lanes → 16 hex
  characters, because `Math.imul` reproduces the 32-bit product exactly where a 64-bit
  hash would need BigInt and invite a silent divergence;
- orbs placed by an LCG seeded from the shard, spelled out identically in both languages,
  because `Math.random()` would make every browser a different game.

Measured 2026-11-02 on `docs/METTHEW/reference-shards/highend_duel`:
`--forge` → golden `1c045e596f950543`; headless Chrome loading the same file printed
`golden: 1c045e596f950543 OK`; `?play=900` collected all 3 orbs in 900 ticks. The test that
asserts this is `tests/test_shardex.py::test_the_browser_computes_the_same_golden_hash_and_can_play`,
skipped when no browser is present.

## The tournament surface (what a champion actually touches)

```json
{ "sim_hz": 60, "gravity": 18.0, "speed": 6.0, "jump": 7.0,
  "arena": 8.07, "orbs": 3, "difficulty": 1.12, "seed": 4220286397 }
```

Edit any of those, reload, and the golden hash changes — so a bracket can publish
"`speed=9, orbs=9` is the grand final config, hash `…`" and anyone can reproduce the
arena that hash names. `--verify` recomputes independently and refuses a bundle whose
claimed hash does not recompute, whose shell still carries `__FLAME_JSON__`, or whose
shell does not name its own shard.

The determinism partition from `docs/METTHEW/shard.schema.json` is respected in the only
way this tool can respect it: **the hash covers sim state, never a frame.** Lighting,
glow and the camera are presentation and are not in the hash.

## Refusals, and the incident each one prevents

| refusal | what it stops |
| --- | --- |
| a source that is not a directory → exit 2 `NO-SOURCE` | an empty mirror reported as a small game |
| a source with no files → `EMPTY-SOURCE` | "0 files" read as a setting |
| payload over the cap → shard `REFUSED` with the byte count | a shard that fails the validator later, when nobody remembers which slice it was |
| a shard with no entrypoint → `NO-ENTRYPOINT` | forging an arena from nothing, and calling it a game |
| a slice cited as a game → `state: SLICE`, `golden_run` all zeros | the word "game" doing work the artifact has not earned |
| `--verify` on a golden that does not recompute → `REFUSED` | a bundle that lies about being the bundle that was proven |

## What is next (and what would be dishonest to promise)

1. **Ruleset extraction** (L4, research): recovering movement, collision and win
   conditions from a game's code. Until that exists, no document here says "your game".
2. **Brackets** (L4, mechanical): a round is a config plus a hash plus a replay — the
   pieces exist, the ranking does not.
3. **Signed results**: `author_pubkey` is in the schema and empty in every forged
   manifest. A result file that anyone can edit is a result file nobody can rank.
4. **Multi-shard arenas**: today one shard forges one arena. A game with 40 shards is 40
   arenas, and telling them apart is the next real design question, not a config flag.

## Intake: when a real game tree arrives (SHX-7 / SHX-8)

The selftest fixture is four files. A real tree is where the heuristics fail, so the
intake is a documented run, not a vibe:

```bash
python Project_SHARDEX/shardex.py --mirror <game> --out .shardex
python Project_SHARDEX/shardex.py --shatter --mirror-file .shardex/mirror.json --out .shardex
python Project_SHARDEX/shardex.py --forge .shardex/shards/<one> --out flame
python Project_SHARDEX/shardex.py --verify flame
```

And the record must answer, in numbers: how many files and bytes were seen (and how many
were skipped, with names); how many groups became shards; how many shards were refused and
why; which shard was forged and its golden hash; and whether headless Chrome printed that
same hash. A second identical run must produce byte-identical shard ids — if it does not,
the pipeline is reading something it does not declare.

What is expected to break, listed so a fix is measured rather than improvised: a game whose
whole logic sits in one directory (one giant group), non-UTF8 or over-long Windows paths,
symlink loops, duplicate basenames collapsing inside one shard, asset directories that
dominate the payload, and shards whose entrypoint is a shader or a data file rather than
code. **The low-end ceiling is not raised to make a tree fit** — the ceiling is the
contract the validator enforces, and moving it turns a measurement into a preference.

## Transubstantiation: a 2D animation becomes a 3D one (SHX-6, narrow slice)

`shardex.py --forge` generates an arena *from* a shard: its own `fidelity` field says the
original rules are not extracted. `transubstantiate.py` is the other direction and does one
thing: read a 2D canvas animation, **extract the rules that make it move**, and emit a 3D
scene obeying the same rules on the same clock.

```bash
python Project_SHARDEX/transubstantiate.py --extract <animation.html> --out .transub/rules.json
python Project_SHARDEX/transubstantiate.py --forge .transub/rules.json --out .transub
python Project_SHARDEX/transubstantiate.py --bind-shard .transub/shards/<id>/shard.json \
        --forge .transub/rules.json
NODE_PATH=C:/Users/clint/node_modules node tools/capture_transubstantiation.js .transub 240
python Project_SHARDEX/transubstantiate.py --verify .transub
python Project_SHARDEX/transubstantiate.py --selftest
```

**The extraction contract is five rules, and a missing one is a refusal, not a default.**
A deterministic clock (`window.__step(ms)` or `draw(p)`), phase constants (`GROW`/`LABEL`/
`HOLD`), a seed (`mulberry32(<int>)`), an entity table (`LIMBS = [["name", side, spread,
"#hex", "path"], …]`), and a root `branch(...)` call with a length-shrink expression. Each
extracted rule records the **line that proves it**. `--selftest` runs a positive fixture, a
negative control (a source with no clock, which must be REFUSED) and a tamper check.

**What verification actually checks is a differential between two implementations.**
`golden3d.json` holds a quantised geometry digest and the projected state at three ticks (one
in GROW, one in LABEL, one in HOLD). `capture_transubstantiation.js` reads `window.__geo()`
and `window.__state(tick)` from the live page and writes `browser_probe.json`; `--verify`
refuses when the two disagree. That refusal earned its keep on the first run: the Python port
of mulberry32 was wrong (476 segments against the browser's 489), then the digest stream was
wrong (`%.4f` vs `toFixed`, and a `|`-joined list against a `|`-suffixed one). Both were
found by the cross-check and by nothing else.

Measured on `docs/YGGDRASIL_CLEAVE.html` (sha256 `81e1dabe48223b87…`, 10 limbs, seed
20261028, 30 000/8 000/7 000 ms): **489 segments, 822 leaves, geometry digest
`69b9d1ad4c93d173`, browser cross-check MATCH**, 240 frames → 1920×1080 H.264, 3.6 MB, 24 fps,
decoded and read back. The `*.mp4` and the frames are gitignored local artifacts; regenerate
with the four commands above.

**Fidelity, stated rather than implied:** phases, seed, entity table and branch law are
carried with evidence. No pixel, colour ramp, sprite or label is carried. In 3D the limb
`spread` rule becomes the outward tilt of a ring around the trunk, because the 2D source fans
limbs across the single axis it has; that mapping is a documented interpretation, not an
extracted constant.

## Live mutation: an image becomes a mesh, and the mesh changes while it renders

`transubstantiate.py` translates a program whose rules are readable. An image has no rules to
read, so the honest representation is **sampled data plus a graph that moves**, and the graph is
mutated by operators applied to a scene that is already running.

```bash
NODE_PATH=C:/Users/clint/node_modules node tools/sample_image.js --in <image> --out .live/field.json
python Project_SHARDEX/meshscene.py --forge .live/field.json --out .live
NODE_PATH=C:/Users/clint/node_modules node tools/capture_transubstantiation.js .live 180 \
        --live .live/ops.json
python Project_SHARDEX/meshscene.py --verify .live
```

**Pipeline.** Image → field (`96x54` luma/hue/Sobel, sha256 of the source, plus a 256-entry Q15
sine table) → mesh (`576` neurons, `1201` synapses for a 640×480 photograph) → scene with one
mutation entry point, `window.__mutate(op)`.

**The operators** (`ops.py`): `warp`, `sprout`, `prune`, `palette`, `extrude`. Each is a pure
function of (mesh, op); each exists twice, in Python and in the page; each op's digest is
recorded by the page *after* it applies, and `--verify` replays the log and must reproduce every
digest. Measured on 2026-11-02, applied between frames 30/60/90/120/150 of a 180-frame render:

| seq | op | mesh digest | neurons/synapses |
| --- | --- | --- | --- |
| 0 | warp amp 3.0 | `51fdace00bdd1bfe` | 576 / 1201 |
| 1 | extrude ×3 | `9c89b09f0553e46d` | 576 / 1201 |
| 2 | palette +120° | `b799871e7759a070` | 576 / 1201 |
| 3 | sprout 300 | `a37949c2ead7f094` | 576 / 1501 |
| 4 | prune <0.6 | `1894f7d8c9908126` | 576 / 1108 |

`--verify` → VERIFIED, op chain `d23155c2cf6a8324…`, all five digests reproduced in Python, base
mesh and three projected golden states matching the page exactly.

**Three defects came out of this build, all of the same shape** — a measurement that disagreed
while the thing being measured was correct. The projection quantised at 1e-2, then at 1e-4, while
the page used 1e-3; the base mesh digest matched all along, so only the states failed and only
three of them. The lesson is written into the code: when a digest compares two implementations,
the ruler is part of the contract.

**Two gates, both measured.** `FLAT-FIELD` refuses a field whose *mean edge energy* is under 6.0
(the first gate used `std(luma) >= 40` and refused every dark UI panel in this tree while
accepting a solid fill); a solid fill measures 0.0, panels 8.2–17.3, a photograph 32.6. And
`OP-INVALID` refuses an operator carrying a field it does not use, because an ignored parameter
is a mutation that quietly did less than its author believed.

**Fidelity.** The mesh is a *representation of the sampled field*, not a reconstruction of the
image: no pixel is drawn, and the neurons sit on a block lattice. What is carried is structure
(where edge energy was), colour (sampled hue per cell) and relief (luma as depth) — and what is
verified is that both implementations agree about every one of those after each mutation.

## A question this pipeline has to answer honestly: images, and mid-flight mutation

> Could a shard be built from a **single image**, and could modifications — morph, mutate,
transmogrify — be applied **mid-flight** while it renders?

Mirroring an image directory already works (`--mirror` classifies `.png`/`.jpg` as `asset`
and carries it for provenance, never executes it). Everything after that is unbuilt, and the
honest answer separates the three parts:

1. **Image → rules.** A new extractor (`shardex-image-rules-v1`), because the current
   contract is a *clock and a branch law* and an image has neither. It needs a height field
   (luminance or edge energy on a grid), a palette from quantised hues, and a symmetry axis.
   No new dependency is required: the capture harness already runs Chromium, so the decoder
   is `drawImage` + `getImageData` in the page and the field arrives as JSON.
2. **Mid-flight mutation.** This is the part the current scene *nearly* has and does not:
   `draw(p)` is a pure function of tick, so a mutation layer would sit between tick and draw
   as `{at_tick, warp, palette_shift, scale, spin}` and be **golden-hashed like the base
   scene** — a mutation that cannot be verified is a change nobody can review. Nothing writes
   into a running scene today; changing the scene means re-forging it offline.
3. **Fully rendered.** Already true, and measured: the tick clock is driven from outside the
   page, so 240 frames encode to H.264 and decode back. "Fully rendered mid-flight mutation"
   is one layer above a renderer that already works.

So: possible, half-built, and the half that exists is the hard half (determinism, golden
hashes, refusal, cross-language verification). Treat the image extractor and the mutation
seam as the next increment, not as features.
