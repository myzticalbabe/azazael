# AZAZAEL — Lessons Learned: Import Optimization Session

> **Date:** 2026-06-01  
> **Focus:** Reducing discover_worms() and NCM startup overhead  
> **Key Result:** 8.3s -> 0.51s (16x), 36.2s -> 2.37s (15x)

---

## LESSON 1: Always Profile Before Optimizing

The original assumption was that BINARY_ANALYSIS (4.18s) and METACLUSTER/CLUSTERWORMS (2.01s each) were the only bottlenecks. The **real** bottleneck turned out to be PamsRecorder's HTTP timeout (18 calls x 2s = 36s) — invisible until we profiled the NCM loop specifically.

**Takeaway:** Profile at multiple levels — module import, function execution, and subsystem integration. The biggest win came from a 2-line cache fix in PamsRecorder, not the module split.

---

## LESSON 2: Lazy Imports Are Simple But Need Discipline

The `_get_pams()` pattern is trivial (6 lines), but:
- All callers must be updated to use `_get_xxx()` instead of the old variable
- Sentinel values (`False` for failed imports) are critical to avoid retrying on every call
- Thread safety requires a lock if multiple threads can trigger lazy init simultaneously
- The sentinel pattern means: `if pams: pams.record_event(...)` — `None` and `False` are both falsy

---

## LESSON 3: HTTP Timeouts Are Silent Killers

A single `requests.post(timeout=2)` is harmless. 18 of them = 36s. The fix was trivial (cache the failure state), but discovering the root cause required:
1. Measuring NCM.discover_all_natures() total time (36.2s)
2. Instrumenting each _record() call to find per-call timing
3. Tracing the PamsRecorder code path to find the HTTP timeout

**Takeaway:** Any HTTP call in a loop needs a failure cache. `_pams_unreachable` with periodic retry is the right pattern.

---

## LESSON 4: Module Splitting Is Worth It

BINARY_ANALYSIS went from 4.18s to 0.002s import time by splitting into sub-modules with lazy imports. The key insight: only 20% of the file's functionality is used in most sessions (get_summary()). The heavy PE/ELF parsing is rarely needed.

**Takeaway:** Don't pay for what you don't use. Lazy import patterns let modules declare their capabilities without paying the initialization cost.

---

## LESSON 5: Fast-Path Checks Eliminate Loop Overhead

The `discover_worms()` dir() loop was visiting every module attribute to find @register_worm classes — even though the decorator had already registered them during import. A 5-line fast-path check eliminated this overhead entirely.

**Takeaway:** If a system has two paths to the same result (decorator + discovery), optimize the common case (decorator) and fall back to the slow path only when needed.

---

## LESSON 6: The Python 3.14t Console Hates Unicode

Multiple `UnicodeEncodeError` crashes occurred when printing emoji/checkmarks to the Windows CLI. The SOP correctly mandates ASCII-only output (`OK`, `FAIL`, `[DONE]`).

**Takeaway:** Always use ASCII characters in CLI output on Windows. Never use ✓, ✗, ⚡, or similar — they WILL crash on `sys.stdout.write()`.

---

## LESSON 7: Test Infrastructure Pays for Itself

The 45 new tests (17 + 28 parse/tool tests + 8 integration tests) caught zero regressions — but they provide confidence that the module split didn't break anything. The conftest.py PAMS cache warm-up prevents every test file from paying the 2s HTTP timeout.

**Takeaway:** When refactoring, add tests that exercise the refactored surface. Even simple smoke tests catch structural issues (wrong imports, missing functions, broken APIs).

# AZAZAEL — Lessons Learned: Desktop Projects Standalone Session

> **Date:** 2026-06-01 (afternoon session)
> **Focus:** Making all 14 Desktop projects standalone + LlamaServer setup + openmono 3.14t audit
> **Key Result:** 14/14 Desktop projects now have standalone launchers

---

## LESSON 8: Every Desktop Project Needs a run.py with a status Command

Before this session, 6 projects were stubs or data-only with no entry point. After adding `run.py` launchers with consistent commands (status/start/stop/build), all 14 projects are independently operable. The `status` command is the universal default — it lets anyone quickly assess project health.

**Takeaway:** Standardize on `python run.py status` as the universal entry point for all projects. It costs 20 lines of code and saves hours of confusion.

---

## LESSON 9: TOML on Windows — Always Use Forward Slashes

Windows paths like `C:\Users\...` contain `\U` which TOML interprets as a Unicode escape sequence (`\Uxxxx`). This silently breaks config parsing. The `llama-server/config.toml` had 6 paths with backslashes — the TOML parser failed and the Rust server fell back to non-existent default paths, causing 503 errors on chat completions.

**Takeaway:** All TOML config files on Windows MUST use forward slashes: `C:/Users/clint/...`. This is a footgun that produces no visible error — the parser just fails silently.

---

## LESSON 10: Python HAS_* Flags Must Always Be Initialized Before try/except

`eve_unleashed_app.py` had `HAS_PYNVML` defined only inside the try block with no `= False` initializer. Every other `HAS_*` flag in the file had proper initialization. When pynvml wasn't installed, the variable was undefined, causing `NameError` at module level.

**Takeaway:** Always write `FLAG = False` before `try: import x; FLAG = True`. The `except: pass` pattern requires a default value.

---

## LESSON 11: Import Hygiene — Module-Level Imports Only

Two Desktop project `run.py` files (PAMS, WSL_CrossExplorer) had `import urllib.request` inside functions. Moving them to module level is cleaner, faster (no re-import on every call), and follows Python conventions.

**Takeaway:** Always place imports at the top of the file. If an import might fail, use try/except at module level with a flag, not lazy imports inside functions.

---

## LESSON 12: Rust Binaries Need Their Working Directory for Config

The Rust `llama-server` reads `config.toml` from the current working directory. Running it from a different directory means it silently falls back to defaults. The run.py launcher now `cd`s to the project directory before starting.

**Takeaway:** Always document the working directory requirement for binaries that read relative config files. The launcher should handle this automatically.

---

## LESSON 13: Organize Scattered Files Into the Project Directory

Desktop had 4 llama-related files scattered loose (llama_client.py, launch_llama_stack.ps1, build_llama_all_backends.bat, llama-server.lnk). Moving them into `Desktop/LlamaServer/` via the `cleanup` command consolidated everything. The `run.py` launcher also auto-creates the client if missing.

**Takeaway:** Loose scripts on Desktop are a code smell. Every project should have a dedicated directory with a `run.py` entry point. Use a `cleanup` command to one-shot organize.

---

## LESSON 14: openmono.ai Is .NET, Not Python — Audit Before Assuming

The 3.14t audit revealed openmono is a .NET 10.0/C# project with Python 3 only as a Docker dependency for MCP servers. Zero Python threading code exists. The file-picker and code-searcher agents were essential for confirming this before making unnecessary changes.

**Takeaway:** Always verify the tech stack before auditing for language-specific features. A project in a Python workspace isn't necessarily a Python project.
