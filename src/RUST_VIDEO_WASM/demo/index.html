One music video, four places the Rust/WASM can live

Every panel below runs the same clip. What changes is which layer decodes it and which layer owns the pixels.

idle

The <video> element does the H.264 and AAC work. Rust receives 1024 PCM samples, computes 32 band energies with a Hann-windowed DFT, and renders an additive field at 60 fps — 118 KB of WASM for the whole visual layer. This is the only architecture here that streams a file of any length.

idle

No media element at all: the frames are JPEGs inside one AVFB blob, decoded by jpeg-decoder compiled into the module. It works, and it is the wrong default for a song — the blob is 0.18 MB/s — about 38 MB for this track at 320×180, roughly twice the 19.35 MB mp4 that holds it at 480p, because stills are not inter-coded.

idle

The useful architecture: the browser decodes and Rust rewrites the frame. Each frame is drawImage → getImageData → process_frame_rgba → putImageData. Swap in VideoFrame from WebCodecs to remove the two CPU copies.

idle

A packed AVRD stream — w·h·3 raw bytes per frame, parsed and widened to RGBA inside the module. The container and the pixel layout are Rust; the decode is not, and claiming otherwise would need a full H.264 entropy decoder, which no production-grade pure-Rust implementation exists to supply.
